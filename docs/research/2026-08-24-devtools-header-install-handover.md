# Handover: devtools headers and an event-tracer capability marker

**Date:** 2026-08-24
**Target repo:** `executorch-runtime-dist`
**Requested by:** `djl-executorch-engine`, for
`docs/superpowers/specs/2026-08-24-executorch-devtools-profiling-design.md` §2 (Phase 0)
**Status:** not started — this is the gate on all engine-side work

Everything below is written to be pasted into a fresh agent session rooted in
`executorch-runtime-dist`. It assumes no knowledge of the engine repo. Every factual claim carries
the command that establishes it, so nothing here has to be taken on trust.

---

## What you are being asked to do

Three changes to the ExecuTorch runtime distribution, then a `v1.4.1-3` release:

1. **Install the devtools headers** in the `devtools` tarballs, so a consumer can `#include`
   `ETDumpGen` rather than only link it. (Required.)
2. **Add an `event_tracer=on|off` key to BUILDINFO**, so consumers have an authoritative capability
   signal instead of inferring one. (Required — reasoning in §3.)
3. **Install flatcc's `flatcc_builder.h`.** (Second priority; not a blocker for Linux consumers.)

Optionally, as a separate workstream: publish `devtools` rows for Windows (§8).

## 1. Why — the consuming use case

`djl-executorch-engine` is adding opt-in profiling: a model loads with an ExecuTorch `ETDumpGen`
event tracer attached, accumulates an ETDump across its forwards, and hands the bytes to the caller
for offline analysis with ExecuTorch's Python `Inspector`. The engine will ship a `devtools` runtime
on Linux as its single artifact — measured cost of a devtools runtime with no tracer attached is
+138 KB of shipped `.so` and under 0.35% steady state, so a second artifact was not justified.

To construct an `ETDumpGen` the engine must include
`executorch/devtools/etdump/etdump_flatcc.h`. It cannot.

## 2. Current state — the header gap

The devtools tarball **links** but does not **include**. Extract any devtools tarball and observe:

```bash
ls  lib/libetdump.a lib/libflatccrt.a                      # both present
ls  include/executorch/                                    # extension  kernels  runtime
ls  include/executorch/devtools/                           # No such file or directory
grep -c 'add_library(etdump' lib/cmake/ExecuTorch/ExecuTorchTargets.cmake   # 1
```

So `find_package(executorch)` yields a usable imported `etdump` target — with
`INTERFACE_INCLUDE_DIRECTORIES` pointing at `${_IMPORT_PREFIX}/include` — whose headers were never
installed there.

This is upstream ExecuTorch's gap, not something this repo dropped. In the ET checkout,
`devtools/etdump/CMakeLists.txt` installs the targets with no header `FILE_SET`:

```cmake
install(
  TARGETS etdump flatccrt
  EXPORT ExecuTorchTargets
  DESTINATION ${CMAKE_INSTALL_LIBDIR}
  INCLUDES DESTINATION ${_common_include_directories}
)
```

`INCLUDES DESTINATION` only records an include path on the exported target; it copies no files.

**Do not suggest that the consumer vendor the header.** It pulls
`data_sinks/buffer_data_sink.h`, `data_sinks/data_sink_base.h`, and the flatcc include tree behind
it, and that set would have to be re-synced by hand at every pin bump.

## 3. Current state — the capability-signal gap

The engine needs to know at build time whether the runtime it links can actually trace. The obvious
test, `if(TARGET etdump)`, happens to work today:

```bash
# logging tarball
ls lib/libetdump.a                                                          # absent
grep -c 'add_library(etdump' lib/cmake/ExecuTorch/ExecuTorchTargets.cmake   # 0
# devtools tarball
grep -c 'add_library(etdump' lib/cmake/ExecuTorch/ExecuTorchTargets.cmake   # 1
```

But it works by accident. Upstream's `add_library(etdump ...)` and its `install(TARGETS ...)` are
**unguarded**, and the root `CMakeLists.txt` adds the subdirectory in both branches:

```cmake
if(EXECUTORCH_BUILD_DEVTOOLS)          # ~line 587
  add_subdirectory(devtools)
...
  if(NOT EXECUTORCH_BUILD_DEVTOOLS)    # ~line 996
    add_subdirectory(devtools)
```

Nothing upstream promises the logging tarball will keep excluding `etdump`. If that exclusion ever
lapses, a consumer gating on `TARGET etdump` would build a logging runtime believing it can profile.
Tracing would then silently produce empty dumps, because `EXECUTORCH_ENABLE_EVENT_TRACER=OFF`
compiles the tracer hooks out of `Method::execute`. Empty output, no error, no clue.

**Please make the signal explicit.** BUILDINFO already carries exactly this kind of key — `usdt=on`
— generated by `scripts/gen-buildinfo.sh`, whose body is a single here-doc. Add:

```
event_tracer=on|off
```

driven by the same source of truth that sets `-DEXECUTORCH_ENABLE_EVENT_TRACER` in
`scripts/lib/variants.sh`, not by a second copy of the variant list. The engine will read that key
and hard-fail its configure if it disagrees with `TARGET etdump`, converting a future silent
mismatch into a build error.

## 4. Recommended mechanism for the headers

This repo already has the right machinery; the work is choosing between two existing precedents.

**Preferred: a source patch**, via `patches/` and `scripts/patch-et-sources.sh`. That script applies
each patch idempotently (`git apply --reverse --check` as the already-applied test) and treats a
non-applying patch as a hard error with a message telling the next person to regenerate against the
new pin. Three patches live there now, so a fourth follows a worn path. The patch adds a header
install to `devtools/etdump/CMakeLists.txt` covering `etdump_flatcc.h`, `data_sinks/*.h`, and the
flatcc-generated schema headers under `${DEVTOOLS_INCLUDE_DIR}`.

**One trap specific to this patch.** Because the subdirectory is processed in *both* branches (§3),
an unconditional install rule would place devtools headers in the `bare` and `logging` tarballs too.
That breaks acceptance criterion 3. Guard the new install rule on `EXECUTORCH_BUILD_DEVTOOLS`
explicitly rather than relying on the subdirectory not being reached — it is reached.

**Alternative: copy into the prefix after install**, the way the Highway `LICENSE` is handled in
`build-runtime.sh` ("copy it into the prefix or hard-fail"). Simpler to write, but it needs its own
variant guard, it duplicates knowledge of which headers `etdump_flatcc.h` transitively needs, and it
drifts silently when upstream adds one. Prefer the patch; fall back to this only if the patch proves
unstable across pins.

Either way `scripts/package.sh` needs no change: it stages `include` from the prefix wholesale
(`for m in lib include LICENSE THIRD-PARTY-NOTICES`), so anything installed into the prefix ships.

## 5. Verification gate

Follow the convention this repo already states — prove the change survived the build, do not merely
prove a file was edited. `scripts/package.sh` already does exactly this for the OpenVINO delegate:
it refuses to package when a platform claims OpenVINO but `lib/$_ov_archive` is missing.

Add the parallel assertion: when `VARIANT` is `devtools`, require
`include/executorch/devtools/etdump/etdump_flatcc.h` in the staged tree and fail packaging if it is
absent. That way a patch that stops applying cannot ship a tarball whose consumer contract is
quietly broken.

## 6. Tests

Test conventions are `test/*.test.sh`, driven by `test/run.sh`, with `test/assert.sh` helpers and
patch fixtures under `test/fixtures/etpatch/`. `test/patch_et_sources.test.sh` is the model to
follow for a new patch, and `test/buildinfo.test.sh` for the new BUILDINFO key.

Assert behaviour, not diff shape — no greps for current wording:

- The devtools patch applies to a pristine tree and is idempotent on an already-patched one.
- After a devtools install, the prefix contains the headers; after a `logging` install, it does not.
- BUILDINFO carries `event_tracer=on` for `devtools` and `off` for `bare`/`logging`, and that value
  agrees with the `-DEXECUTORCH_ENABLE_EVENT_TRACER` flag in the same file's `cmake_flags`.
- `package.sh` fails when a devtools prefix lacks the header.

## 7. Acceptance criteria

1. Every `devtools` tarball contains `include/executorch/devtools/etdump/etdump_flatcc.h` and the
   `data_sinks/` headers it includes.
2. A consumer calling `find_package(executorch)`, linking the `etdump` target, and including
   `etdump_flatcc.h` compiles — header and imported target agree.
3. `bare` and `logging` tarballs are unchanged in scope: no devtools headers, no `etdump` target, no
   `libetdump.a`. The Windows tarballs the engine ships today must be untouched.
4. BUILDINFO carries `event_tracer=on` for `devtools` and `off` for `bare` and `logging`, sourced
   from the same place as the cmake flag.
5. Second priority: `flatcc_builder.h` is installed. Rationale — the ETDump buffer returned by
   `get_etdump_data()` is caller-owned, and ExecuTorch's own reference consumer
   (`examples/devtools/example_runner/example_runner.cpp`) releases it with plain `free()`. That is
   correct on POSIX but undefined under MSVC, where flatcc allocates with `_aligned_malloc`; the
   portable release is `flatcc_builder_aligned_free`, which is in `libflatccrt.a` but whose
   declaration ships nowhere. Installing the header now turns a future Windows arm into a one-line
   call instead of a hand-written `extern "C"` against a vendored third-party symbol. No licensing
   work: `THIRD-PARTY-NOTICES/third-party_flatcc_LICENSE` already ships.

## 8. Optional separate workstream — Windows devtools rows

Independent of the above and not a blocker. The pin currently publishes `devtools` for
`linux-x86_64` and `linux-aarch64` only; Windows has `logging` and `logging…-static`. If Windows
devtools is published, the engine needs **both** CRT rows — `windows-x86_64` and
`windows-x86_64-static` — because it links the `/MT` static row so its DLL needs no VC++
redistributable. A single `/MD` devtools row is not usable by that consumer.

If this lands in the same release, criterion 5 above stops being second priority and becomes
required: the engine's Windows arm needs `flatcc_builder_aligned_free`.

## 9. Release and handback

Release process is a tag push: `.github/workflows/release.yml` triggers on `v*-*`, and
`scripts/derive-version.sh` parses `v<etver>-<pkgrev>`. So this ships as **`v1.4.1-3`**.

The consumer then replaces `native/cmake/EtRuntimePin.cmake` wholesale with the release's pin asset,
re-applies its comment header, and re-runs `./native/gen_clangd_db.sh`. Nothing else is needed from
this repo.

## 10. Non-goals

- Do not change what `bare` or `logging` ship. The engine ships `logging` on Windows today and that
  artifact must not move.
- Do not add engine-side profiling code here. This repo's deliverable is the runtime distribution.
- Do not upstream the header install to pytorch/executorch as a prerequisite. Worth doing on its own
  merits and worth filing, but the release cannot wait on an upstream review cycle.
