# ExecuTorch runtime pin bump: v1.3.1-10 -> v1.4.1-2

**Date:** 2026-08-22
**Producer release:** [`v1.4.1-2`](https://github.com/measly-java-learning/executorch-runtime-dist/releases/tag/v1.4.1-2)
(ExecuTorch 1.4.1, torch 2.13.0+cpu)

This is sub-project **A** of a two-part migration. Sub-project **B** — enabling OpenVINO on
Windows — gets its own spec and plan. The split exists because a bump that must go green on three
platforms should not also be carrying a new platform capability: when something fails, the cause
has to be unambiguous.

## 1. What the release changes for this consumer

Four things, of which only the second and third need design.

**ExecuTorch 1.4.1.** Upstream verified before publishing that the vendored
`workspace_size_bytes` accessor keeps its spelling and its read-only semantics, that the XNNPACK
submodule pin did not move, that every cmake option we depend on survives, and that the glibc floor
stays at 2.28 (cp312 `torch==2.13.0+cpu` wheels exist for `manylinux_2_28` on both arches and for
`win_amd64`). Consumer-side this is therefore a sweep of version literals, not an integration.

**The pin's OpenVINO interface changed shape.** `ET_RUNTIME_OPENVINO_{PLATFORM,URL,SHA256}` is now
the *deprecated* legacy form, describing `linux-x86_64` alone; removal is tracked as
[executorch-runtime-dist#48](https://github.com/measly-java-learning/executorch-runtime-dist/issues/48).
The live interface is per-platform rows — `ET_RUNTIME_OPENVINO_URL_<platform>` /
`ET_RUNTIME_OPENVINO_SHA256_<platform>` — read through `et_runtime_openvino_url(<platform> url sha)`,
which returns empty strings rather than aborting when a platform has no bundle. `native/build.sh`
greps exactly the deprecated trio today. That is the dangerous case: it keeps working against this
release and silently ignores every non-Linux bundle, so the failure is invisible until the
deprecated vars disappear.

**OpenVINO now exists on Windows** — both the delegate and a runtime bundle. The Windows runtime
tarballs ship `openvino_backend.lib`, and the release publishes
`openvino-runtime-2025.4.1-windows-x86_64.tar.gz` with both Windows pin rows pointing at it (the
wheel's DLLs are `/MD` regardless of how a consumer links, so one bundle serves both CRT rows). Its
shape differs from Linux: six unversioned DLLs, no symlink, no `hwloc` entry (folded into
`tbbbind_2_5.dll`), and `OPENVINO_LIB_PATH` naming `lib/openvino_c.dll`. This is sub-project B.

**License attribution fixes.** The release ships Eigen's license alongside `libeigen_blas.a` and
the licenses for the tokenizers dependency stack. Both arrive inside the runtime tarball's
`THIRD-PARTY-NOTICES/`.

## 2. Scope

**In scope**

- Adopt pin `1.4.1-2`.
- Migrate `native/build.sh` off the deprecated OpenVINO vars onto per-platform rows, behind an
  explicit engine-side supported-platform gate.
- Sweep ExecuTorch version literals across Java, shell tests, and docs.
- Bump the four exporter scripts and regenerate the build outputs they own.
- Verify the new license notices reach the staged tree.
- Drive the three-platform verification gate.

**Out of scope**

- Windows OpenVINO support: `OpenVinoRuntime`'s library list and platform messaging, the Windows
  staging leg, the `windows-x86_64-openvino` capability jar, CI matrix rows. Sub-project B.
- Throughput comparison against 1.3.1. An ET minor bump can move performance; measuring it is a
  separate decision.
- Re-exporting the committed `.pte` fixtures. See §5.

A links the Windows OpenVINO delegate *incidentally* — `native/CMakeLists.txt` links
`openvino_backend` whenever that target exists, and on 1.4.1 it exists on Windows. A stages no
Windows bundle and claims no Windows OpenVINO support. The user-visible effect is that
`EtNative.backendRegistered` starts reporting the delegate present on Windows, which moves a
Windows user from "re-export is your only option" to "supply a runtime" — the third state the
engine already models for `linux-aarch64`.

## 3. Pin adoption

Replace `native/cmake/EtRuntimePin.cmake` wholesale with the release asset, then re-apply this
repo's consumer comment header. The SHA256 changes are the supply-chain review gate; the header is
re-applied by hand because the asset is generated and carries none of it.

Two claims in the current header die and must not be carried forward:

- the paragraph describing `ET_RUNTIME_OPENVINO_*` as "contract C10 ... the bundle exists for
  `ET_RUNTIME_OPENVINO_PLATFORM` only" — that is the deprecated form, and the new file documents
  the selector itself;
- the line stating the OpenVINO rows are unconsumed here. They have been consumed since the
  OpenVINO work landed; the line was already false before this bump.

After the pin lands, re-run `./native/gen_clangd_db.sh`. Nothing else refreshes the clangd
database, so it otherwise keeps resolving against 1.3.1 headers with no warning.

## 4. The OpenVINO selector migration

`native/build.sh` today asks one question: *does the pin's single OpenVINO platform equal the row I
am building?* That question no longer has a well-defined answer, because the pin now describes
several platforms. It splits into two independent ones.

**Does this engine support an OpenVINO bundle on this platform?** An explicit list in `build.sh`,
holding `linux-x86_64` today. This is a statement about what the Java layer can load, and it is
deliberately engine-side: without it, "what we support" would be a side effect of what the producer
happened to publish, and B's capability would arrive by accident rather than by decision.
Sub-project B's diff here is one entry.

**Does the pin publish a row for it?** Grep `ET_RUNTIME_OPENVINO_URL_<row>` and
`ET_RUNTIME_OPENVINO_SHA256_<row>`. Empty means "no bundle for this row", which is legitimate —
`linux-aarch64` will never have one — so this mirrors `et_runtime_openvino_url`'s non-aborting
semantics, not the tarball selector's `FATAL_ERROR`.

Both must hold to stage. When either fails, the skip message names which one, so that
"supported but unpublished" and "published but unsupported" are distinguishable in a build log;
today Windows is the second and `linux-aarch64` is a permanent third case (neither).

The lookup key is the **platform identity**, not the pin row — the opposite of the ExecuTorch
tarball, which is row-keyed because the CRT flavour is part of its identity. An OpenVINO bundle is
per platform: the wheel's DLLs are `/MD` whatever a consumer links, so one bundle serves both
Windows rows and the pin expresses that with an *alias* row whose value is a CMake variable
reference:

```cmake
set(ET_RUNTIME_OPENVINO_URL_windows-x86_64-static "${ET_RUNTIME_OPENVINO_URL_windows-x86_64}")
```

A row-keyed grep would return that literal text, because shell cannot dereference a CMake variable.
Keying on the platform resolves to a real URL on every platform and never reads an alias row. To
keep that from silently regressing, the resolver rejects any resolved URL that is not literal
(`https://…`) rather than handing an unexpanded reference to `curl`, and the test asserts the
resolved Windows URL is literal.

Grep-parsing is retained rather than routing the lookup through CMake. `build.sh` already parses the
pin this way for every other value, and the alternative — extending the `ET_PRINT_RESOLUTION`
machinery so CMake calls the selector and prints the result — buys correctness we do not currently
lack at the cost of a configure round-trip inside the staging step and a new script/CMake contract.

**Test.** `native/tests/` gains a behavioural check that a supported-but-unpublished row and an
unsupported-but-published row each skip staging rather than stage. The second case is exactly
today's Windows state, so it is testable now, on Linux, with no Windows hardware. Per this repo's
convention the test asserts the behaviour, not the wording of the message.

## 5. Version sweep and fixtures

**Java.** `EtEngine.EXECUTORCH_VERSION` -> `1.4.1`, and the two tests that assert the literal
against it: `EtEngineStatsTest` and `EtEngineStatsJmxTest`.

**Shell.** `native/tests/cmake_resolution.sh` carries `1.3.1` in its stem and URL assertions plus a
`/download/v1.3.1-10/` release assertion; all move to `1.4.1` / `v1.4.1-2`. That release assertion
exists because the ET version is unchanged across pkgrevs, so it is the only thing that catches a
pin left at the wrong release — it must move, not be dropped.

**Prose.** `native/scaling.sh` comments, `CLAUDE.md`, and the `docs/` reference set.
Point-in-time records under `docs/research/` and prior specs/plans are not swept: they record what
was true when written.

**CI.** No edit. Nothing in `.github/` names an ExecuTorch version.

**Exporters.** All four PEP-723 headers (`export_mobilenet.py`, `export_mobilenet_openvino.py`,
`export_stress_model.py`, `export_w5_add_models.py`) move to `executorch==1.4.1` with the
torch/torchvision pair `uv` resolves for it. The gitignored outputs they own — the MobileNetV2
`.pte`/`.pt` pair, the unplanned MobileNetV2 variant, the w5 add models — are regenerated, which
costs nothing.

**Committed fixtures stay exported at 1.3.1.** That is `src/test/resources/models/stress/`
(`.pte` plus its golden digests, which are only correct because they were generated together),
`src/test/resources/models/named/`, `native/spike/*.pte`, and the two upstream-published fixtures
`src/test/resources/lstm/` and `src/test/resources/models/openvino/`. Re-exporting them would make
every committed `.pte` match the runtime version, but it would destroy the evidence that a
1.3.1-exported `.pte` runs on the 1.4.1 runtime — which is the compatibility property users
actually depend on, and which the gate then proves for free.

`StressGoldenTest`'s inline `"1.3.1"` is a parser input in a hand-written JSON string, not coupled
to the engine version, and does not move.

**Contingency.** If `LstmModelIT` or `openvinoTest` fails against the 1.3.1 fixtures, that is a
real incompatibility rather than a stale literal. A then refreshes those two upstream fixtures to
their 1.4.1 assets (`etnp-lstm-fixtures-1.4.1.tar.gz`,
`etnp-openvino-fixtures-1.4.1-2025.4.1.tar.gz`, both published in this release) and records what
broke. This is the one condition that widens A's scope, and it is the reason those two fixtures are
named separately from the ones we export ourselves.

## 6. License attribution

`native/build.sh` copies the resolved runtime tree's `LICENSE` and `THIRD-PARTY-NOTICES/` wholesale
into the staged `licenses/` directory and hard-fails when either is absent. The Eigen and tokenizers
fixes are additions inside `THIRD-PARTY-NOTICES/`, so they should flow through with no code change.

That is a hypothesis, so A verifies it rather than assuming it: diff the staged notices tree against
the 1.3.1 one and confirm an Eigen notice and the tokenizers-stack notices are present and new. The
Eigen one matters most — whole-archiving `optimized_native_cpu_ops_lib` pulls MPL-2.0 code into our
`.so` through `optimized_kernels -> cpublas -> eigen_blas`, which makes the notice an obligation on
*our* distribution, not merely on the tarball.

The check that keeps them arriving is the existing hard-fail plus a `native/tests/` assertion that
the staged notices tree is non-trivial. Matching on exact filenames is deliberately avoided: the
Eigen notice's name is path-derived upstream and can shift with the vendoring path, so a filename
grep would be a test that fails for the wrong reason.

## 7. Verification gate

**linux-x86_64** — `./native/local_build_wrapper.sh` into a *fresh* build directory (a reused CMake
cache across an ET version change produces failures that read like compiler bugs), then
`./gradlew test`, `./gradlew openvinoTest`, `./native/local_build_wrapper.sh native/build_qa.sh`
(ASan + UBSan), `native/ubsan_gate.sh` in both phases, and every `native/tests/*.sh`.

**linux-aarch64** — the same container build plus `./gradlew test` on `radxa-dragon-q6a.local`.

**windows-x86_64** — by hand on winbox: delete the 1.3.1 build trees, run `native/build.sh` from
Git-Bash under an active MSVC dev shell, `native/tests/check_windows_crt.sh` over both the shim and
QA trees, then `gradlew.bat test`. `check_windows_crt.sh` is the real CRT gate — MSVC does not
reliably diagnose a mismatch. Drive the session in short chunks with `</dev/null` rather than one
long-timeout script.

**Notices** — the §6 diff.

No benchmark runs.

     `ET_RUNTIME_OPENVINO_PLATFORM` comparison silently declined to fetch for any other row. That
     section is what A implements.

   Its **Windows guidance is not there yet**. The file was edited in the Windows publication
